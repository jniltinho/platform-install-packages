# Incremental lab workflow

Read this for installation/functional progression. Resolve exact current paths,
versions, machine identities and allowed actions from reviewed receipts; filenames
below are navigation aids, not automatically trusted executable instructions.

1. **Recognize the lab.** Confirm target identity and current package/runtime/
   source state against the selected receipt. Keep production `.20` outside all
   experiments. Before mutations require the approved coherent recovery checkpoint.
2. **Install a bounded next component.** Reuse reviewed pilot helpers under
   `tools/php83/pilot83/`, exact offline package plan and explicit phase scope.
   Batch and Elasticsearch incremental derivatives keep workers held and record
   full_acceptance=false. Inspect their actual gates before execution. Missing
   complete seed audit alone need not block held installation; target, source,
   privacy, dependencies and recovery checks still do.
3. **Establish a safe real session.** Audit active logging before passwords, KS,
   cookies or authenticated URLs. Use synthetic accounts and prove needed allow/
   deny behavior. Do not invent permission grants merely to make tests pass.
4. **Run the short end-to-end path.** After separately reviewed worker release,
   exercise login -> upload -> terminal job/flavor state -> READY -> thumbnail ->
   HLS manifest/segment and progressive Range. Confirm the actual profile and
   storage destinations. Bound queues/time and contain failures; a page200 or
   READY flag alone is not playback acceptance.
5. **Expand and close.** Reuse the unchanged deterministic fixtures for FullHD,
   HTTPS with trusted CA, search, UI and Go console. Then complete the original
   distro/reprovision/reboot/performance/upgrade/recovery acceptance matrix.
   Preserve unmet cases rather than narrowing the task to observed happy paths.

## Existing evidence to reuse selectively

- Config39 collector: prepared read-only SELECTs, private comparisons in memory,
  fixed public result codes. It does not cover all defaults/save/customData/enum/
  XSD behavior. Read its current design and receipt, not just an exit0.
- Permission reuse fixture: actual source methods with DB/peer doubles; no proof
  of persisted or effective runtime authorization. Separate extracted methods
  from methods actually executed.
- Full168 media fixture: versions reflect declared DC assumptions and doubles.
  Join FileSync with qualified object type/id/subtype, not an unqualified ID.
- Dynamic enum API-to-core lookup can save a new enum. Diagnostic collection
  needs an authenticated fixed SELECT, not application bootstrap/apiToCore.

Do not convert all observed mismatches into repairs. Check setter transforms,
SQL defaults, serialization, DC and lifecycle before asserting a defect.
Unknown mappings may remain explicit gaps during partial read-only diagnosis.
